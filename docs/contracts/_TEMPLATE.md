# Контракт: часть А и часть Б

<!--
Контракт нужен, когда систему делают две команды или два агента: например, бэкенд и мобильное
приложение, или «мозг» и «мотор» робота. Этот документ единственный источник правды по протоколу,
обе стороны реализуют его одинаково. Меняется только по согласованию обеих сторон.
-->

Версия протокола: **1** (поле `v` в каждом сообщении).

## Транспорт

_Как связаны стороны: HTTP, WebSocket, очередь. Кто сервер, кто клиент. Адреса и порты по умолчанию._

## Формат сообщений

### Запрос (от А к Б)

```json
{ "v": 1, "type": "command", "id": "uuid", "name": "...", "params": {} }
```

| Поле | Тип | Описание |
|---|---|---|
| `v` | int | Версия протокола |

### Ответ или событие (от Б к А)

```json
{ "v": 1, "type": "event", "id": "uuid", "status": "completed", "reason": null }
```

## Каталог команд

| `name` | `params` | Счастливый путь | Отказы и ошибки |
|---|---|---|---|
| _…_ | _…_ | `accepted`, потом `completed` | `rejected: busy`; `failed: timeout` |

## Семантика

- **Жизненный цикл:** _какие статусы и в каком порядке, какой из них терминальный._
- **Корреляция:** _по какому полю сопоставлять ответы с запросами, что делать с ответами на устаревшие запросы._
- **Конкурентность:** _сколько операций одновременно, что будет со второй._
- **Аварийные команды:** _что принимается всегда (например, `stop`)._

## Коды ошибок

_Полный перечень `reason` по статусам._

## Живучесть

_Таймауты, heartbeat, поведение при реконнекте._

## Примеры обмена

```
→ {"type":"command","name":"...","id":"A"}
← {"type":"event","id":"A","status":"accepted"}
← {"type":"event","id":"A","status":"completed"}
```

## Мок

_Где лежит референсная реализация второй стороны для разработки без неё и какие тестовые хуки она понимает._
